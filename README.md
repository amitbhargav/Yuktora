# Yuktora 🎯
Your AI job search co-pilot. Score jobs, tailor resumes, track every application. Built in Bengaluru.

Live: https://yuktora.vercel.app

---

## 🛠️ System Architecture & Tech Stack
* **Frontend:** Multi-page vanilla JS/HTML5/CSS3 (`index.html`, `signin.html`, `app.html`, `pricing.html`, `privacy.html`) with shared `styles.css`.
* **Hosting:** Vercel — auto-deploy from `main`, with serverless functions under `/api`.
* **AI Proxy:** `/api/anthropic` Vercel Function proxies Claude API calls using a server-side `ANTHROPIC_API_KEY`, gated behind a Supabase session JWT check. Users don't need their own key. Depends on `@supabase/supabase-js`, declared in `package.json`. A `/api/gemini` function also exists — pending audit to decide whether to keep both providers or consolidate.
* **Database & Auth:** Supabase (Mumbai region) — passwordless magic-link sign-in with RLS-scoped `user_profiles` and `tracked_jobs` tables.
* **Development:** VS Code + Cline extension.

### Phase 3.18: Visa Sponsorship Detection Accuracy (Shipped)
* **The bug:** `fetchLiveJobs()` flagged a job as visa-sponsored (🌍 badge, folded into the fit score) whenever the word "visa" appeared *anywhere* in the JD text — including inside explicit non-sponsorship statements. A real example caught in testing: a KPMG posting stating "*KPMG LLP will not sponsor applicants for U.S. work visa status... no sponsorship is available for H-1B, L-1...*" was shown as a confirmed-sponsored 100% match.
* **Fix:** replaced the substring check with `detectVisaSponsorship()` — requires an explicit positive statement ("will sponsor", "sponsorship available", etc.); negation ("will not sponsor", "unable to sponsor") or plain silence both resolve to *unconfirmed*, never assumed true. Verified against the exact KPMG text plus 11 other scenarios via unit tests.
* **Stronger than a badge fix — international jobs are hidden, not just unbadged:** added `isAbroadJob()`, comparing the job's country against the candidate's profile location (skipping remote roles, and any case with insufficient location data, to avoid over-filtering). A job outside the candidate's country with unconfirmed sponsorship no longer appears in Job Search results at all; the "Analysed jobs" summary now reports how many were hidden and why (e.g. "2 hidden — no visa sponsorship confirmed").
* **Country matching is deliberately conservative:** only resolves a location's country when it matches a known-country whitelist — a bare city name like "Bangalore" (no country suffix) never gets treated as an unrecognised "country" that would false-positive as abroad against "India".

### Phase 3.20: Visa Detection Follow-up — Region Recognition, Live Rescoring (Shipped)
* **Location detection was too narrow:** Phase 3.18's `isAbroadJob()` only recognised specific country names — a JSearch result location like `"europe"` (a region, not a country) didn't resolve to anything, so the abroad-hiding check silently skipped it and the job slipped through unfiltered. `KNOWN_LOCATIONS` now also recognises broad regions (Europe, EMEA, APAC, Middle East, Gulf, North America, LatAm, etc.) as distinct from a candidate's home country.
* **New signal — JD text can require local eligibility without ever saying "visa" or "sponsor":** added `requiresLocalWorkAuthorization()`, matching phrasing like "must have EU work eligibility" or "right to work in the UK required." `jobNeedsHiding()` now hides a job if *either* it's abroad with unconfirmed sponsorship, *or* the JD demands pre-existing local work rights — confirmed sponsorship always overrides both.
* **Fixed the "match breakdown looks broken" bug:** live-fetched jobs were scored once at fetch time and frozen forever — a job scored 100% purely on title match (because the profile had zero skills configured *at that moment*) stayed frozen at 100% with an unhelpful "Skills not found: none flagged" breakdown even after skills were added later. Added `rescoreHeuristicJobs()`, which recomputes score, visa status, and the breakdown text against the *current* profile on every render — tagged only onto heuristic-scored jobs (`scoreSource: 'heuristic'`); AI-scored jobs from Paste JD are left alone since re-scoring those would cost a real Claude call. `matchBreakdown()` also now explicitly says "No skills set in your profile yet" instead of the ambiguous "none flagged" when the profile has zero skills.
* **Verified** with 12 unit tests (including the exact "europe"-location and "EU work eligibility" scenarios reported) plus a live headless-browser run reproducing the full before/after: a stale 100%-match "europe" job with no confirmed sponsorship gets hidden, then reappears with a live-recalculated score once the JD confirms sponsorship and a matching skill is added to the profile.

### Phase 3.21: Free-Tier AI Fallback — Gemini (Shipped)
* **Problem:** `/api/anthropic` is the only AI backend, gated on a paid Anthropic account's credit balance — when that balance hits zero, every AI feature (Resume Tailor, Analyse & Score, Rejection AI) fails outright with Anthropic's raw billing error.
* **Built out `api/gemini.js`** (previously an empty stub left for this exact purpose — see Phase 3.6): same Supabase JWT gate and `ai_usage_logs` logging as `api/anthropic.js`, calling Google's free-tier Gemini API (`gemini-2.0-flash` → `gemini-1.5-flash` fallback). Its response is normalized to the identical `{ content: [{ text }] }` shape `api/anthropic.js` returns, so nothing downstream needs to know which provider actually answered.
* **Frontend `claude()` now tries both, in order:** Anthropic first (generally the stronger model), automatically falling back to Gemini on any failure — a bad response, a network error, or a billing block. If both fail, the surfaced error includes both providers' reasons, not just the first one, so nothing gets silently swallowed.
* **Requires a one-time manual step** (same pattern as `ai_usage_logs`/`recruiter_leads`): get a free key at aistudio.google.com (no credit card required) and add it to Vercel as `GEMINI_API_KEY`, then redeploy so the serverless functions pick it up.
* **Verified** with isolated fallback-chain tests (Anthropic succeeds / Anthropic fails+Gemini succeeds / both fail with combined error / Anthropic network error+Gemini succeeds) and a response-shape check against a realistic Gemini API payload — all passing. Not verified against a live Gemini key/quota, since none exists in this environment; recommend a real end-to-end check once `GEMINI_API_KEY` is set.

### Phase 3.23: Stale-Job Self-Healing + Gemini Model Fix (Shipped)
* **Root cause of "the europe jobs are still showing 100% and aren't hidden":** Phase 3.18/3.20's fixes only *recomputed* visa/score for jobs explicitly tagged `scoreSource: 'heuristic'` — but that tag didn't exist before Phase 3.20 shipped, so every job already sitting in a user's browser from before then (the exact "europe" jobs reported) was skipped entirely by both `rescoreHeuristicJobs()` and the hiding check, keeping their original wrong `visa: true` (from the old pre-Phase-3.18 substring-match bug) forever.
* **Fix — stop trusting stored `visa` for anything except explicitly-sourced jobs:** `jobNeedsHiding()` now re-derives visa status fresh from `detectVisaSponsorship(j.jd)` for every job *except* those tagged `'ai'` (Paste JD — Claude's own judgment) or `'manual'` (Manual entry — the user's own hand-checked `jm-visa` checkbox, added as a new tag this phase specifically so that authoritative signal never gets silently overridden). Everything untagged (all legacy data) is treated as heuristic by default. `rescoreHeuristicJobs()` follows the same rule and migrates legacy jobs to `scoreSource: 'heuristic'` as it touches them, so this is a one-time self-heal per job, not a recompute-forever cost.
* **Verified** with a headless-browser run seeding the exact reported scenario — two untagged legacy jobs with stale `visa: true` (including the literal HiTHIUM/LJB "europe" jobs from the screenshots) plus one `scoreSource: 'manual'` job with a real user-confirmed sponsorship not mentioned in its JD text — confirming the two stale jobs self-correct and hide while the manual entry's authoritative signal is preserved untouched.
* **Also addressed — Gemini model names:** the reported `models/gemini-1.5-flash is not found for API version v1beta` error meant that model ID is no longer valid for this key. Widened `api/gemini.js`'s fallback list to `gemini-2.5-flash → gemini-2.0-flash → gemini-2.0-flash-001 → gemini-1.5-flash-latest`, and the final error (if every model fails) now names which ones were tried. **Not independently verified** — no live Gemini key/quota exists in this environment; if AI features still fail after this redeploys, the actual error message will now say which model names were attempted, which is the next diagnostic step.
* **Not addressed yet, flagged for a decision:** the free heuristic match breakdown (title/skill-substring based) will never match the depth of a dedicated ATS scanner or Claude's own "Analyse & score with AI" report — that gap is by design (the heuristic is the free/instant tier, deep analysis is the AI tier), but both AI providers being down simultaneously (Anthropic credit balance + the Gemini model issue above) meant *only* the shallow heuristic was ever visible, which is what actually read as "not working." Whether "Manual entry" (Job Search's third Add-a-job tab) is still worth keeping is also an open question — raised mid-session, not yet decided either way.

### Phase 3.25: Cloud-Overwrite Data Loss Fix + Dead Dashboard Widget Hidden (Shipped)
* **Real data-loss bug found:** the Applications tracker appeared broken/stuck at one old test entry no matter how many jobs got added via "Add to tracker." Root cause: `fetchFromSupabase()` was called automatically on *every* `SIGNED_IN` or `TOKEN_REFRESHED` Supabase auth event — which fires on every page reload and on background token refreshes, not just manual sign-in — and it does a hard `S.apps = [...]` overwrite with zero merge or confirmation. Any tracker entry added locally since the last explicit "Save to Cloud" click was silently wiped the next time the page reloaded.
* **Fix:** the auto-load now only fires when there's genuinely nothing to lose locally (`!S.apps.length && !S.jobs.length` — a fresh browser/device with no local data yet). Once local data exists, only the explicit "Load Data" button can overwrite it. This is a minimal, safe fix, not the full "auto-sync everything" redesign discussed for My Profile (see below) — that's a bigger change still open for a decision.
* **Confirmed and hid a second dead-code panel:** the Dashboard's "AI Match Analytics Engine" (Fit Meter gauge, Keyword Gap Analysis chips, AI Resume Tailor Assistant) was, per its own code comment, "three static UI widgets" — 100% hardcoded markup (fixed "Senior Product Manager," fixed "85% Match," fixed keyword chips like "Product Strategy"/"SQL / Analytics") that `renderDash()` never touches. It showed the same fake numbers regardless of who was signed in, what their real profile said, or whether they'd analysed any job at all — confirmed via a full grep showing nothing in the codebase ever writes to any of its `mae-*` elements except one unrelated Copy button. Hidden (not deleted) via `display:none` on its wrapper pending a decision on whether to wire it to real data or remove it outright.
* **Simplified the Base resume card per explicit request:** dropped the character count and the "Edit extracted text" reveal-link entirely — My Profile now shows a plain "Resume uploaded ✓" (plus detected role, if known) with no path back to viewing/editing the raw extracted text from that card. Upload-only, as asked.
* **Verified** with a headless-browser run: the fake Dashboard widget is confirmed hidden, the resume summary shows no character count and no edit-link element in the DOM, and the auto-load guard condition correctly evaluates to "don't overwrite" when local tracker data exists.
* **Explicitly not built yet — needs a decision, see conversation:** a full My Profile edit/view-lock mode with a single unified "auto-saves to cloud" button (would also make the fix above unnecessary by keeping local and cloud always in sync); a Rejection AI redesign that auto-pulls from the tracker/saved JD/saved resume instead of manual re-entry; and further Gemini API key diagnosis, since widening the model list (Phase 3.23) alone didn't resolve it.

### Phase 3.26: Profile Edit/View Lock + Auto-Cloud-Sync, Rejection AI Redesign, Usage-Limit Clarity (Shipped)
* **My Profile now opens read-only by default.** A single "✏️ Edit profile" button unlocks every field (name/phone/location/LinkedIn/visa checkbox/roles/locations/skills/resume upload); clicking it again while editing becomes "💾 Save profile," which saves locally, pushes to the cloud, and re-locks in one action. Nothing changes by accident anymore.
* **"Save profile" and "Save to Cloud" are unified — the separate topbar button is gone.** `syncToCloud()` now fires automatically after every meaningful local change: profile save, adding a job to the tracker, updating an application's status, deleting one, or adding one manually. It no-ops silently in demo mode / signed out (same guard as the resume-insight extraction), and any real failure still surfaces via `saveToSupabase()`'s existing toast — this isn't a hidden failure mode, just a removed manual step. The topbar's "Load Data" button is kept (renamed "🔄 Refresh from cloud" for clarity on what it actually does — an explicit, deliberate overwrite from the cloud, useful after editing on another device) since automatic *pulling* on every load is still the more dangerous direction (see Phase 3.25's fix above).
* **This also closes the loop on Phase 3.25's tracker data-loss bug more completely:** since local and cloud now stay in sync continuously instead of drifting between manual "Save to Cloud" clicks, there's no longer a window where local has data the cloud doesn't.
* **Rejection AI redesigned — fewer inputs, structured output.** The free-text "Role & company" input, "Job requirements" paste box, and "Resume you submitted" paste box are gone. In their place: a dropdown of your tracked applications (auto-fills role, company, and — new — the original JD, now saved locally on each tracker entry via `addToTracker()`) and your saved base resume, used silently. The only remaining inputs are Rejection stage (a real choice) and an optional rejection message. Output changed from one dense paragraph-per-section text blob to a structured Claude response (`ROOT_CAUSE:` / `GAPS:` / `RESUME_FIXES:` / `STRATEGY:` / `NEXT_ACTIONS:`, pipe-separated lists) parsed into five distinct labelled boxes — Root Cause, a two-column Gaps/Resume Fixes row, Strategy, and Next 3 Actions — instead of a wall of text.
* **The tracker-stored JD is local-only for now** (not added to the `tracked_jobs` Supabase schema) — deliberate scope call to avoid a SQL migration mid-session; it just means Rejection AI's auto-fill won't have JD context for applications tracked before this shipped, or synced fresh from a different device. Can be added to the cloud schema later if cross-device context turns out to matter.
* **"5 Free Uses Left" wasn't self-explanatory** — renamed the Settings card from "Yuktora Pro" to "AI usage limit" and rewrote its copy to state plainly what counts as a "use," that the counter is per-browser (not per-account, not demo-only), and — honestly — that real Pro purchasing isn't live yet (Razorpay still pending per Phase 4), so the only way to remove the cap today is the pre-existing client-side `pro_`-prefix check in the License Key field (not a real license, just what already existed in the code). Added a hover tooltip to the sidebar's usage pill too, and made it clickable through to Settings.
* **Verified** with a headless-browser run covering the full new flow: profile starts locked → Edit unlocks fields → Save re-locks and fires a cloud sync call → adding a job to the tracker stores its JD and fires a sync call → Rejection AI's dropdown populates from the tracker → selecting an application and running analysis produces correctly parsed structured output in all five sections → the old "Save to Cloud" button is confirmed absent from the DOM. Zero console errors.
* **Not resolved — Gemini still failing even with a confirmed, correctly-scoped key.** The user confirmed `GEMINI_API_KEY` is set in Vercel (Production + Preview) and redeployed after Phase 3.23's widened model list shipped, but hadn't yet re-tested at the time of this phase — genuinely unverified whether the wider model list fixed it. If it's still failing, the four-model-name theory is likely wrong and the next suspect is the key's own scope/origin (Google AI Studio vs. Google Cloud/Vertex AI use different auth entirely).
